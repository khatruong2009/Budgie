## 2. Pitfalls reported for framework swaps under the same bundle ID

### 2.1 Storage location and key-name mismatches
- Flutter `shared_preferences` keys carry `flutter.`; native code reading `themeMode` sees nothing. SOURCED: [pub.dev shared_preferences](https://pub.dev/packages/shared_preferences), [flutter/flutter#52544](https://github.com/flutter/flutter/issues/52544), [flutterclutter: read shared preferences from native apps](https://www.flutterclutter.dev/flutter/tutorials/read-shared-preferences-from-native-apps/2021/9753/).
- `flutter_secure_storage` (not used here) uses its own keychain service name/account and, in >= 0.3.x, treats `kSecAttrAccessible` as a strict search filter, so a native reader needs the same `kSecAttrService` and accessibility. SOURCED: [flutter_secure_storage#1164](https://github.com/juliansteenbakker/flutter_secure_storage/issues/1164), [package page](https://pub.dev/packages/flutter_secure_storage). Not applicable unless a future field is added.
- React Native analog: AsyncStorage files moved between `Documents/RCTAsyncLocalStorage_V1` and `Application Support/<bundleID>/RCTAsyncLocalStorage_V1`; Expo used `RCTAsyncLocalStorage`. Same lesson: the new code must open the exact old path. SOURCED: [react-native-async-storage PR 274](https://github.com/react-native-community/async-storage/pull/274/files/7cb5d272503b67792ad261efd4c489007c9bc79d), [Expo AsyncStorage path issue](https://github.com/react-native-community/async-storage/issues/225).
- `path_provider` directories on iOS: Application Support = `<container>/Library/Application Support`, Documents = `<container>/Documents` (no app-name subfolder). SOURCED: path_provider docs above.

### 2.2 Versioning and submission
- `CFBundleVersion` must be strictly higher than any previously uploaded build for that version train, and the version string (`CFBundleShortVersionString`) must not be lower than the live version. Flutter derives both from `pubspec.yaml` (`3.4.0+1` means build number 1 for 3.4.0). The native project must use a marketing version > 3.4.0 (or 3.4.0 with build > every previous 3.4.0 build) and never reuse an uploaded build number. SOURCED: [Apple Community CFBundleVersion thread](https://discussions.apple.com/thread/3572949), [fastlane discussion](https://github.com/fastlane/fastlane/discussions/20743). Repo memory note (`ios-version-bump-stale-xcconfig`) confirms `Generated.xcconfig` staleness on the Flutter side; irrelevant once Flutter is gone but relevant to the rollback build (section 3).
- App Store review looks at the app, not the toolkit; a Flutter -> SwiftUI rewrite is reviewed like any update, and no framework disclosure is required. This is community answers, not Apple staff. SOURCED: [Apple Forums 761979](https://developer.apple.com/forums/thread/761979).
- Minimum deployment target can be raised or kept; users on older iOS just stop getting the update. Current App Store Connect rules (fetched 2026-09-28): apps must be built with Xcode 26+ / iOS 26 SDK (from 2026-04-28), and "iOS and iPadOS apps must target iOS 13 or later" from 2026-09-09. Target 15.0 satisfies this. SOURCED: [Apple: Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/).
- **Privacy manifest**: a native app that touches `UserDefaults` (required-reason API) must ship `PrivacyInfo.xcprivacy` declaring `NSPrivacyAccessedAPICategoryUserDefaults` with reason `CA92.1` (own-app defaults) and, if the widget/app group suite is read, also consider `1C8F.1` (app-group defaults). The Flutter Runner has no `PrivacyInfo.xcprivacy` in `ios/Runner` (it is supplied by plugins). File-timestamp and disk-space APIs also need reasons if used. Enforced at upload since 2024-05-01. SOURCED: [Apple news: Privacy updates for App Store submissions](https://developer.apple.com/news/?id=3d8a9yyh), secondary write-up [Donny Wals](https://www.donnywals.com/how-to-add-a-privacy-manifest-file-to-your-app-for-required-reason-api-usage/). The specific reason codes `CA92.1`/`1C8F.1` are from Apple's required-reason API page which I could not render here; treat the code strings as SOURCED (secondary) and re-check against the Apple page when writing the manifest.
- Keep: bundle ID, team, App Groups entitlement, URL scheme `budgetapp`, usage-description strings, Sign in / capabilities matching the App ID (the provisioning profile already includes the group for both app and extension IDs). INFERRED.

### 2.3 Data protection class differences
- Default class for both stacks is Protected Until First User Authentication (see end of section 1). A native rewrite that switches to `Data(contentsOf:)`/`FileHandle` still gets the same default. If someone adds `.completeFileProtection` to writes, all reads while the phone is locked fail. SOURCED (Apple docs above).
- `NSFileProtectionComplete` as default plus prewarm is the documented worst case: DTS says to stop using `UserDefaults` for anything meaningful in that configuration. SOURCED: [Apple Forums 667959 "Lost data in UserDefaults"](https://developer.apple.com/forums/thread/667959).

### 2.4 Prewarming and launch before first unlock
- Apple's own description: the system may prewarm an app "after a device reboot, and periodically"; "prewarming creates your process and loads the libraries your app links against, then suspends your process without allowing any application code to run." SOURCED: [About the app launch sequence](https://developer.apple.com/documentation/uikit/about-the-app-launch-sequence).
- Observed reality differs from that description: developers report `application(_:didFinishLaunchingWithOptions:)` **does** run in some background launches (Live Activity / push / prewarm) with the device still locked, and Apple's own text about it is disputed. SOURCED: [RevenueCat community: iOS 15 prewarming clarification](https://community.revenuecat.com/sdks-51/ios-15-prewarming-clarification-1605), [openradar FB9780579](https://openradar.appspot.com/FB9780579), [Christian Selig, Beware UserDefaults (2024-10)](https://christianselig.com/2024/10/beware-userdefaults/), [Michael Tsai summary](https://mjtsai.com/blog/2024/10/07/launching-before-userdefaults-is-available/).
- Failure mode: while protected data is unavailable, `UserDefaults` **does not throw**; reads silently return defaults (nil/false/0). Code that treats "missing" as "first run" then overwrites or wipes real data. Real-world casualties: Apollo day-streak resets/logouts (Selig), Amplify secure-storage wiping valid Cognito credentials after `UserDefaults.bool(forKey:)` returned false ([amplify-flutter#7395](https://github.com/aws-amplify/amplify-flutter/issues/7395)), OneSignal ([PR 1669](https://github.com/OneSignal/OneSignal-iOS-SDK/pull/1669)), Firebase ([firebase-ios-sdk#9869](https://github.com/firebase/firebase-ios-sdk/issues/9869)), pointfree swift-sharing `@AppStorage` ([discussion 59](https://github.com/pointfreeco/swift-sharing/discussions/59)), and a Medium write-up ([iOS Confessions: prewarming logouts](https://theiosdude.medium.com/ios-confessions-episode-2-ios15-prewarming-logouts-and-our-answer-to-the-keychain-not-available-43fcca4420c5)). Also [Apple Forums 685685](https://developer.apple.com/forums/thread/685685).
- Apple DTS guidance (Quinn): do not use `NSUserDefaults` for anything you rely on in code paths that can run in the background; keep your own file whose protection you control; check `isProtectedDataAvailable` before reading; do not equate empty with first run. SOURCED: Forums 667959 and Tsai page above. `isProtectedDataAvailable` is documented as "true if data protection is enabled and the device is currently locked"[sic, i.e. meaning content protection is active], and files with `complete`/`completeUnlessOpen` keys cannot be read while it is false ([UIApplication.isProtectedDataAvailable](https://developer.apple.com/documentation/uikit/uiapplication/isprotecteddataavailable)); `UIApplication.protectedDataDidBecomeAvailableNotification` posts when it flips ([doc](https://developer.apple.com/documentation/uikit/uiapplication/protecteddatadidbecomeavailablenotification)). Note: Selig doubts `isProtectedDataAvailable` reliability and recommends a probe-read approach; the pointfree discussion shows a latch pattern combining the flag with a probe.
- **Existing Flutter mitigation to port**: `lib/storage/protected_data_gate.dart` + `AppDelegate.swift` (channel `budget_app/protected_data`) already gate initialization on `isProtectedDataAvailable` and `protectedDataDidBecomeAvailable`. The native app must replicate this: no reads/writes of the store, no "first run" onboarding decision, and no widget-suite writes until protected data is available, and must treat a read error as "unknown", never as "empty store". The Flutter store already distinguishes "file not found" from other read errors (`readIfPresent` contract), which is the right shape. (VERIFIED by reading the file.)
- Keychain during the same window: `kSecAttrAccessibleAfterFirstUnlock` items are unreadable before first unlock after boot; reads fail with `errSecInteractionNotAllowed` (-25308). SOURCED: Apple kSecAttrAccessibleAfterFirstUnlock page above, [Apple Forums 724267](https://developer.apple.com/forums/thread/724267).
- Widgets run in a separate process and can also be woken before first unlock; the widget's `UserDefaults(suiteName:)` read of `cashFlow` returning nil renders as "never written". Today that is a placeholder, not data loss. INFERRED from the same mechanism.

### 2.5 Other reported gotchas
- Dynamic quick actions from the old version linger until first launch of the new one (section 1).
- Widgets randomly blank after updates on iOS 17 (Forums 743135): reload timelines at first launch with `WidgetCenter.shared.reloadAllTimelines()`. INFERRED mitigation; the Flutter AppDelegate already does this after every `updateCashFlow`.
- Sim vs device: TN2285 warns that installing with Xcode can create a "frankenbuild" unlike a real App Store update and masks watchdog crashes; test the update path with TestFlight (old Flutter build first, then native build with a higher build number) before shipping. SOURCED: [TN2285](https://developer.apple.com/library/archive/technotes/tn2285/_index.html).
- "The most common update bug is the new version not handling data created by previous versions… your app must handle data from **any** previous version" because users skip releases. SOURCED: TN2285. The Flutter store already has `schemaVersion` 2 plus a migration from the v1 `SharedPreferences` envelope and per-feature keys (`atomic_financial_store.dart`); a user who skipped 3.x releases could still have legacy `flutter.transactions` etc. in `NSUserDefaults`. The native app should decide deliberately whether to import those legacy keys (Flutter deletes them only after verified migration).

## 3. Rollback: installing an older Flutter build over the native app

- **App Store users cannot downgrade.** The App Store only serves the current version; iOS has no rollback. Non-App-Store routes (old IPA via iTunes 12.6.5/Configurator, MDM, TestFlight older build) are workarounds. SOURCED: [Apple Community: revert to previous app version](https://discussions.apple.com/thread/255068136), [Apple Community: downgrade without losing data](https://discussions.apple.com/thread/255076288), [NinjaOne](https://www.ninjaone.com/blog/how-to-downgrade-apps-on-ios-and-android-devices/). The only supported "rollback" is shipping a new build (higher build number) that contains the old behavior, or removing the release from sale / phased release halt in App Store Connect (INFERRED; App Store Connect docs not fetched).
- **Dev / TestFlight rollback data behavior**: installing a build with the same bundle ID over another keeps the data container regardless of which build is newer. VERIFIED on the Simulator with two ad-hoc test apps sharing one bundle ID (build 2 installed over build 1, then build 1 over build 2): `simctl install` returned 0 and the container contents (Application Support file, `NSUserDefaults` value, app group file) were preserved in both directions. On device, `xcrun devicectl device install app` / Xcode Run are documented by TN2285 as behaving *unlike* the App Store path, so re-test on hardware (INFERRED). TestFlight refuses lower build numbers of the same version (SOURCED via the CFBundleVersion threads above).
- **What the old Flutter build will do with native-written data** (from `atomic_financial_store.dart`, VERIFIED by reading):
  - It accepts `financial_store_v2.json` only if the first line is JSON with `format == "budgie-financial-store"`, `schemaVersion` int and `<= 2`, `revision` int, `payloadLength` int equal to the payload byte count, `payloadChecksum` string equal to FNV-1a-64 (offset `0xcbf29ce484222325`, prime `0x100000001b3`, lowercase 16-hex, zero padded) over the raw payload bytes; then newline (0x0A); then the sections JSON.
  - If both primary and backup fail those checks, Flutter renames them to `*.corrupt-<millis>` and falls through to migrate from `SharedPreferences` (which after a successful earlier migration has been cleared) -> the user sees an **empty app**, with the real data hiding in `.corrupt-*` files. So the native writer must NOT bump `schemaVersion` above 2, change `format`, or change the header field types, if rollback to the current Flutter build has to work. Any native-only fields must live inside sections as additive keys the Flutter models ignore (Flutter `fromJson` already tolerates missing keys per AGENTS.md; unknown-key tolerance not verified for every model, INFERRED).
  - The checksum covers exact payload bytes (not a re-encoding), so byte-level JSON differences between Swift and Dart output do not break verification (section 5).
  - The newest readable `revision` wins between primary and backup, so the native writer must increment `revision` monotonically and keep the backup in the same rotation.
- `NSUserDefaults` `flutter.*` keys written by Flutter remain if native code neither renames nor deletes them; keep them if rollback support is wanted.
- Keychain / App Group values persist too; the rolled-back build would need the same group entitlement.

## 4. Testing upgrade paths on the Simulator

All results below are VERIFIED with a throwaway ad-hoc-signed UIKit app built with `swiftc -target arm64-apple-ios15.0-simulator` (two bundles "App1"/"App2", same bundle ID `com.khatruong.migtest`, `CFBundleVersion` 1 and 2) on a freshly created simulator that I deleted afterwards (no existing simulator or repo file was touched). The apps wrote a file to Application Support, a `flutter.themeMode` default, and logged `isProtectedDataAvailable`.

- **`xcrun simctl install <udid> App.app` over an existing app of the same bundle ID keeps the data.** The Application Support file and the `NSUserDefaults` value written by build 1 were read by build 2. The data container *directory UUID changes on every install* (contents moved), so never cache the path; re-query. Downgrade (build 2 -> build 1) also succeeded (rc 0) with data intact. `simctl uninstall` then install started empty (`prior_file=<none>`).
- **Locate containers**: `xcrun simctl get_app_container <udid|booted> <bundle-id> data` (also `app`, `groups`, or a specific group id). Result for the data container was a path under `~/Library/Developer/CoreSimulator/Devices/<udid>/data/Containers/Data/Application/<uuid>`. Caveat: `get_app_container … groups` and `… <group.id>` printed nothing / a usage error for my ad-hoc-entitled test app (entitlements applied by `codesign --entitlements`, not by a provisioning profile, so simctl's metadata did not list the group). The group path was still resolvable in-process via `FileManager.containerURL(forSecurityApplicationGroupIdentifier:)` and lives under `…/data/Containers/Shared/AppGroup/<uuid>`. For a real Xcode-built app with a properly signed group entitlement, `groups` should work (INFERRED); otherwise `find ~/Library/Developer/CoreSimulator/Devices/<udid>/data/Containers/Shared/AppGroup -name .com.apple.mobile_container_manager.metadata.plist | xargs grep -l group.com.khatruong.budgetbuddy`.
- **Injecting `NSUserDefaults`: `xcrun simctl spawn <udid> defaults write <bundle-id> <key> <value>` does NOT work for a sandboxed app's standard defaults.** It writes `~/Library/Developer/CoreSimulator/Devices/<udid>/data/Library/Preferences/<bundle-id>.plist` (the simulated user's global Preferences), not the container's `Library/Preferences/<bundle-id>.plist`; the app never saw those keys (VERIFIED). Reliable method (VERIFIED): `xcrun simctl terminate` the app, **`xcrun simctl shutdown <udid>`**, edit `<data container>/Library/Preferences/<bundle-id>.plist` with a script (Python `plistlib`; do NOT use `plutil -replace/-insert` with keys containing dots like `flutter.onboarding_completed` because dots are key-path separators), `xcrun simctl boot <udid>`, launch. Editing the plist while the simulator is booted was unreliable: cfprefsd's cached copy hid my keys from the app (only visible after a reboot of the sim), and `killall cfprefsd` is not available inside the sim (`simctl spawn <udid> killall cfprefsd` fails with ENOENT). For domains in an App Group suite the same applies to `Shared/AppGroup/<uuid>/Library/Preferences/group.…plist`.
- **Snapshotting real Flutter data for the upgrade test**: `xcrun simctl help` lists `install_app_data <udid> <xcappdata>` (replaces the whole container contents; app is terminated first) and `clone`. A downloaded `.xcappdata` from a real device (Xcode > Devices > Download Container) can be restored into a simulator this way (SOURCED from the built-in help text; not run). The repo memory file says the physical iPhone holds real data, the iPhone 17 Pro sim holds seeded fake data: run the Flutter build there first, `simctl get_app_container … data` and copy the container aside, install the native build, and diff.
- **Simulating prewarm / protected data unavailable: not possible with simctl.** VERIFIED: in the simulator `UIApplication.isProtectedDataAvailable` was `true`, and `FileManager` `.protectionKey` on the written file was `nil` (the simulator does not apply iOS Data Protection classes). `simctl help` has no lock/passcode/first-unlock verb (subcommands: addmedia, appinfo, boot, clone, create, delete, diagnose, erase, get_app_container, getenv, help, icloud_sync, install, install_app_data, io, keychain, launch, list, listapps, location, logverbose, openurl, pair, pair_activate, pbcopy, pbpaste, personalization, privacy, push, reboot, rename, runtime, shutdown, spawn, status_bar, terminate, ui, uninstall, unpair, upgrade). `simctl privacy` covers calendar, contacts, location, photos, media-library, microphone, motion, reminders, siri, all: it can grant/revoke/reset microphone for the bundle ID (`xcrun simctl privacy <udid> reset microphone com.khatruong.budgetbuddy`) but has no notifications or Face ID service. `simctl keychain <udid> reset` wipes the sim keychain. Consequence: the protected-data gate must be tested (a) by unit tests with an injected `isProtectedDataAvailable` provider, (b) with a debug launch argument/env var (`SIMCTL_CHILD_<NAME>=1 xcrun simctl launch …` passes env vars to the app, SOURCED from `simctl help launch`) that makes the gate report "unavailable" for N seconds then post the notification, and (c) on a real device: enable a passcode, reboot, do NOT unlock, and trigger a prewarm/background launch (Live Activity is Selig's 100% repro path; otherwise a push/`content-available`/widget refresh) then read Console logs. Face ID cannot be tested on the Simulator except via the Features > Face ID menu.
- **Widgets/quick actions on the Simulator**: widget placement survival across `simctl install` can be tested by placing the widget (see repo memory `sim-widget-gallery-automation`), installing the new build with the same kind, and checking it still renders; Simulator is not a guarantee given the frankenbuild caveat (SOURCED TN2285), and the blank-widget bugs were reported mainly on devices (Forums 743135: "widgets work fine in simulator but fail on physical devices").

## 5. Swift vs Dart JSON byte compatibility

Sources of truth:
- Dart `jsonEncode` writes numbers with `number.toString()`: [sdk/lib/convert/json.dart, `writeNumber`](https://github.com/dart-lang/sdk/blob/main/sdk/lib/convert/json.dart) (`_sink.write(number.toString())`). SOURCED + VERIFIED. Dart's [`double.toString` docs](https://api.dart.dev/stable/dart-core/double/toString.html) guarantee round-trip and `-0.0`, but do **not** document exponent thresholds (VERIFIED thresholds below).
- Swift's new `JSONEncoder` (swift-foundation) writes a `Double` as `float.description` and strips a trailing ".0": [FoundationEssentials/JSON/JSONEncoder.swift `number(from:)`](https://github.com/swiftlang/swift-foundation/blob/main/Sources/FoundationEssentials/JSON/JSONEncoder.swift). SOURCED. `Double.description` is SwiftDtoa's shortest round-trip form ([SwiftDtoa.h](https://github.com/swiftlang/swift/blob/main/include/swift/Runtime/SwiftDtoa.h), [PR 15474](https://github.com/swiftlang/swift/pull/15474)).
- `JSONSerialization` escapes `/` unless `.withoutEscapingSlashes` (iOS 13+/macOS 10.15+, SOURCED: [Apple doc](https://developer.apple.com/documentation/foundation/jsonserialization/writingoptions/withoutescapingslashes)); `.sortedKeys` sorts lexicographically (iOS 11+, [Apple doc](https://developer.apple.com/documentation/foundation/jsonserialization/writingoptions/sortedkeys)); swift-foundation `JSONWriter` source escapes `_slash where !withoutEscapingSlashes` ([JSONWriter.swift](https://github.com/swiftlang/swift-foundation/blob/main/Sources/FoundationEssentials/JSON/JSONWriter.swift)). Historic precision differences for `JSONSerialization` doubles: [swift-issues SR-7195](https://github.com/apple/swift-issues/issues/7195).

### 5.1 Number formatting: empirical comparison (VERIFIED)

Scripts (in the session scratchpad, not in the repo): `t.dart`, `t.swift`, `t2.*`, `t3.*` compiled/run with `dart run` and `swift file.swift` on Swift 6.4 / macOS 27 (swift-foundation-based Foundation). Struct with one `Double` field was encoded with `JSONEncoder` (Codable) and `["a": v]` with `JSONSerialization`.

| Value | Dart `toString` = `jsonEncode` | Swift `Double.description` | Swift `JSONEncoder` | Swift `JSONSerialization` |
|---|---|---|---|---|
| 1.0 | `1.0` | `1.0` | `1` | `1` |
| 100.0 | `100.0` | `100.0` | `100` | `100` |
| 0.1+0.2 | `0.30000000000000004` | `0.30000000000000004` | `0.30000000000000004` | `0.30000000000000004` |
| 1e21 | `1e+21` | `1e+21` | `1e+21` | `1e+21` |
| 1e-7 | `1e-7` | `1e-07` | `1e-07` | `9.9999999999999995e-08` |
| 123456789.12 | `123456789.12` | `123456789.12` | `123456789.12` | `123456789.12` |
| -0.0 | `-0.0` | `-0.0` | `-0` | `-0` |
| 5e-324 | `5e-324` | `5e-324` | `5e-324` | `4.9406564584124654e-324` |
| 1.7976931348623157e308 | `1.7976931348623157e+308` | `1.7976931348623157e+308` | `1.7976931348623157e+308` | `1.7976931348623157e+308` |
| 1e20 | `100000000000000000000.0` | `1e+20` | `1e+20` | `1e+20` |
| 1e16 | `10000000000000000.0` | `1e+16` | `1e+16` | (same style) |
| 1e15 | `1000000000000000.0` | `1000000000000000.0` | `1000000000000000` | `1000000000000000` |
| 9007199254740994 (2^53+2) | `9007199254740994.0` | `9.007199254740994e+15` | `9.007199254740994e+15` | n/a |
| 0.0001 | `0.0001` | `0.0001` | `0.0001` | n/a |
| 0.00001 (1e-5) | `0.00001` | `1e-05` | `1e-05` | n/a |
| 0.000012345 | `0.000012345` | `1.2345e-05` | `1.2345e-05` | n/a |
| 1e-6 | `0.000001` | `1e-06` | `1e-06` | `9.9999999999999995e-07` |
| 4.35 | `4.35` | `4.35` | `4.35` | `4.3499999999999996` |
| 1234567.891 | `1234567.891` | `1234567.891` | `1234567.891` | `1234567.8910000001` |
| Float 0.1 via JSONSerialization | n/a | n/a | n/a | `0.10000000149011612` |

Findings:
1. **Never use `JSONSerialization` for money.** It prints 17 significant digits (`4.3499999999999996`) for doubles that round-trip at fewer, and expands 1e-7 to `9.9999999999999995e-08`. Values still parse back to the same double, but bytes differ from Dart and are ugly. Use `JSONEncoder` (or a hand-rolled writer using `Double.description`). VERIFIED.
2. **Integral doubles**: Swift `JSONEncoder`/`JSONSerialization` emit `100`, Dart emits `100.0`. Dart's `jsonDecode('100')` yields `int`, which is fine here: the repo's `fromJson` code uses `(json['amount'] as num).toDouble()` (`transaction.dart:110`, `net_worth_entry.dart:97`, `categorization_rule.dart:48-49`) and `grep -rn "as double" lib` returns nothing (VERIFIED). Any *new* Dart code with `as double` would break on Swift-written data. Conversely Swift `JSONDecoder` decodes Dart's `100.0` into `Int` fields fine on this Foundation (`Int<-1.0 -> 1`, `Int<-1e2 -> 100`, VERIFIED on macOS 27; older OS Foundation may reject, INFERRED, test on iOS 15/16 hardware) and decodes `1` into `Double` fine.
3. **Exponent notation thresholds differ**: Dart switches to exponent form only for magnitude >= 1e21 or < 1e-6 (decimal expansion between; `1e-6` prints `0.000001`, `1e20` prints `100000000000000000000.0`); Swift switches at < 1e-4 (`1e-05`) and >= 2^53 approx (`1e+16`, `9.007199254740994e+15`; `9007199254740992.0` still decimal). Exponent formatting also differs: Dart `1e-7`, Swift `1e-07` (two-digit exponent); both use `e+21` for positive. All of these forms are valid JSON and parse identically in both languages (VERIFIED: Dart `jsonDecode('{"a":1e-07}')` -> `1e-7` double; Swift `JSONDecoder` reads `1e-7`, `1e+21`, `-0`, `5e-324`, `1.7976931348623157e+308`). For a budget app these ranges are essentially unreachable, so differences are cosmetic; nothing requires byte equality because the file checksum is over the writer's own payload bytes.
4. **`-0.0`**: Swift emits `-0`; Dart `jsonDecode('-0')` returns `int 0` (sign lost, harmless); Dart's own `-0.0` decodes as double -0.0 and Swift reads `-0`/`-0.0` as -0.0. Consider normalizing -0 to 0 when writing.
5. NaN/Infinity: Swift `JSONEncoder` throws by default (`Unable to encode Double.nan directly in JSON`); Dart `jsonEncode(double.nan)` throws too (unsupported). Guard money math.
6. Money is `double` on the Dart side (AGENTS.md). Swift should decode to `Double` (not `Decimal`, whose JSON form differs: `Decimal(string: "4.35")` encodes `4.35` but `NSDecimalNumber` via JSONSerialization also gave `0.1`; mixing is unnecessary).

### 5.2 Key order, escaping, non-ASCII (VERIFIED)

Test payload string: `a/b é 😀 "q" \ <newline> U+0001 U+007F U+2028`.

| Aspect | Dart `jsonEncode` | Swift `JSONEncoder` | Swift `JSONSerialization` |
|---|---|---|---|
| Key order | Insertion order of the Map (`{"s":…,"z":1,"a":2,"i":1}` preserved) | Struct property declaration order for synthesized `Codable` (`s,z,a`); dictionaries are hash order unless `.sortedKeys` | Dictionary hash order (random per process); `.sortedKeys` gives lexicographic (`a,i,s,z`), which is **not** Dart's insertion order |
| `/` | not escaped (`a/b`) | escaped as `a\/b` by default; `.withoutEscapingSlashes` gives `a/b` | escaped `\/` by default; same option |
| Non-ASCII (é, emoji, U+2028) | raw UTF-8 | raw UTF-8 | raw UTF-8 |
| U+007F DEL | raw | raw | raw |
| Control chars | `\n`, `\u0001` style (`\b \f \n \r \t` short forms, others `\u00XX`) | same | same |
| `"` and `\` | escaped | escaped | escaped |
| Compact separators | `:` and `,` without spaces | same by default | same by default |

Consequences:
- Byte-identical output to Dart is not achievable with default Swift settings and is not needed: reading is by parser on both sides and the store checksum is computed over the writing side's exact bytes. If a golden byte comparison is wanted: set `outputFormatting = [.withoutEscapingSlashes]`, model sections as ordered structs (declaration order = Dart map insertion order) and post-process numbers. Do not use `[String: Any]` + `JSONSerialization` for the store (unordered, 17-digit doubles).
- Dart `DateTime.toIso8601String()` output is `2024-01-02T03:04:05.678Z` (UTC) or `2024-01-02T03:04:05.678` with **no zone suffix for local time** (VERIFIED). If any stored date came from a local `DateTime`, Swift must parse the zone-less form as the device's local time (`ISO8601DateFormatter` needs `.withFractionalSeconds` and cannot parse a missing zone; use a custom `DateFormatter` with `en_US_POSIX`, or Codable with a custom strategy). The header field `writtenAt` in the store header is `DateTime.now().toIso8601String()` (local, no zone) and is not validated by the Flutter reader.
- Integers: Dart `int` up to 2^63-1 and JSON numbers >2^53 lose exactness only in JS; both Dart VM and Swift `Int` are 64-bit, and Swift decoded `9007199254740993` exactly (VERIFIED).
- Swift on older OS: the `JSONEncoder` measurements are from macOS 27's swift-foundation implementation. iOS 15-17 use the older Foundation (Objective-C/NSNumber-based) `JSONEncoder`; digit-count and integral-double behavior there is NOT VERIFIED here (only iOS 26.5/27.0 runtimes are installed). Run the same tiny encode test on a real iOS 15/16/17 device or older runtime before shipping if byte formats matter, or write the doubles yourself with `Double.description` (stdlib, stable across OS versions, INFERRED) and only use `JSONEncoder` for structure.
